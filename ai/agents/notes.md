<summary><strong>MCP vs A2A vs ACP</strong></summary>


𝗠𝗖𝗣는 에이전트를 도구와 데이터에 연결하기 위한 것입니다. 데이터베이스 쿼리, API 호출, 파일 접근, 외부 시스템과의 상호작용과 같은 기능 발견 및 사용 방식을 표준화합니다.

𝗔𝟮𝗔는 독립적인 AI 에이전트 간의 통신을 위한 것입니다. 에이전트가 서로의 기능을 발견하고, 작업을 위임하며, 정보를 교환하고, 다양한 프레임워크와 환경에서 작업을 조정할 수 있게 합니다.

A2A가 MCP와 함께 어떻게 맞물리는지에 대해 더 깊이 파고들고 싶다면, 여기 훌륭한 분석이 있습니다 → [https://lucode.co/agent-communication-matrix-z7xd](https://lucode.co/agent-communication-matrix-z7xd)

𝗔𝗖𝗣는 에이전트 간 통신을 위한 또 다른 접근 방식으로, RESTful HTTP API, JSON 페이로드, 표준 웹 인프라를 중심으로 구축되었습니다. 이후 A2A로 병합되어 에이전트 상호 운용성에 대한 두 가지 노력을 통합했습니다.

MCP와 A2A는 경쟁자가 아니라 상호 보완적입니다. 에이전트는 도구 접근을 위해 MCP를 사용하고 조정을 위해 A2A를 사용하며, ACP는 A2A로 병합되었습니다.

하지만 MCP와 A2A가 항상 답은 아닙니다. 프로덕션에서 어떤 접근 방식을 사용할지 결정한다면, 이 가이드가 MCP, A2A 또는 다른 것을 언제 사용할지 분석해줍니다

<summary><strong>그래프 엔지니어링, 이제 말로만이 아니라 실제 도구로 나왔다</strong></summary>


- 그래피파이 : AI 코딩 어시스턴트용 스킬, 코드베이스를 지식그래프로 통째로 매핑
- 벡터인덱스아님 : 임베딩 없이 실제 그래프를 순회하는 방식
- 반전포인트 : 코드 파싱은 LLM 안 씀, 완전 로컬 무료

1) 그래피파이라는 오픈소스 도구가 최근 화제임. AI 코딩 어시스턴트(클로드코드, 커서, 코덱스 등)에서 명령어 하나 치면 코드, SQL 스키마, 문서, PDF, 이미지, 영상까지 프로젝트 전체를 지식그래프로 만들어줌. 그담부터는 파일을 매번 grep하는 대신 그래프에 질문하는 방식으로 작업함.

2) 이게 그래프 엔지니어링 개념을 실제 도구로 구현한 사례임. 노드는 코드의 개념 하나하나, 엣지는 그 사이의 관계(호출, 상속, 참조)임. 근데 재밌는 게 코드 파싱 자체는 트리시터라는 파서로 로컬에서 결정론적으로 처리함, LLM 안 씀. 그래서 코드만 있는 프로젝트는 API 비용 0원임. 문서나 이미지처럼 의미 해석이 필요한 것만 LLM한테 넘김.

3) 벤치마크 수치도 근거로 붙일 만함. LOCOMO 데이터셋 기준 recall@10이 0.497로, 비교 대상인 다른 메모리 시스템(0.048, 0.149)보다 훨씬 높게 나옴. 그래프 빌드에 드는 LLM 크레딧은 0인데, 이건 코드 파싱 부분이 로컬 처리라서 가능한 수치임.

4) 반전 포인트. 다들 요즘 RAG 하면 벡터 임베딩부터 떠올리는데, 이 도구는 정반대 접근임. 임베딩도 벡터스토어도 없이 진짜 그래프 구조를 순회함. 그리고 모든 엣지에 “명시적으로 추출됐는지” “추론된 건지” 태그를 달아둬서, AI가 뭘 확실히 아는지 뭘 짐작한 건지 구분할 수 있게 해둠.

정리하면, 프롬프트 잘 쓰는 시대에서 루프 설계 시대로, 이제 그래프 자체를 코드베이스에 적용하는 시대로 넘어가는 흐름이 실제 제품으로 나타난 셈임. 물론 이것도 아직 초기 도구라 대규모 레포에서 얼마나 안정적일지는 더 지켜봐야 함.

<summary><strong>요즘 클로드 코드나 코덱스를 사용해서 시스템을 설계할 때</strong></summary>


하네스 엔지니어링/루프 엔지니어링의 개념에서 더 나아가 그래프 엔지니어링이라는 개념이 많이 언급되고 있습니다

그래프 엔지니어링에 대한 한글 버전 상세 설명을 확인 할 수 있는 유용한 글 같습니다.

## **Graph Engineering**

Loop Engineering 이후 AI를 다루는 법 - Graph Engineering이란 무엇인가.

2026년 7월, AI 에이전트 설계 담론에서 “Loop Engineering is dead. Long live Graph Engineering!”이라는 선언이 빠르게 퍼졌다.

이는 단순한 유행어가 아니다. Prompt Engineering에서 Context, Harness를 거쳐 Loop Engineering으로 이어진 레버리지 이동이 한 단계 더 바깥으로 확장된 결과다.

모델 자체는 점점 commodity가 되고, 진짜 엔지니어링 대상은 **여러 에이전트(또는 노드)가 어떻게 연결되고 협력하는가**로 이동했다.

### **AI 엔지니어링의 계층적 진화**

지금까지의 흐름을 정리하면 대략 이렇다.

- **Prompt Engineering** (2023–24): 단일 요청의 지시를 설계한다. 역할은 운영자(operator).
- **Context Engineering**: 모델이 보는 정보(검색, 메모리, 윈도우)를 설계한다. 역할은 편집자(editor).
- **Harness Engineering**: 도구, 메모리, 샌드박스, 가드레일을 설계한다. 역할은 도구 제작자(toolmaker).
- **Loop Engineering** (2025–초중반 2026): 단일 에이전트가 목표를 향해 반복하는 사이클(관찰–추론–행동–검증)을 설계한다. Verifier, stop condition, 상태 관리가 핵심이다. 역할은 시스템 디자이너.
- **Graph Engineering** (2026년 중반~): 여러 루프(노드)를 연결하는 topology를 설계한다. 역할은 조직 디자이너(org designer).

이 계층들은 서로 대체하지 않는다. 그래프의 각 노드는 여전히 잘 설계된 루프여야 하고, 루프는 좋은 harness와 context 위에 세워진다. 그래프는 그 위 계층이다.

### **Loop Engineering: 단일 개체의 자율성**

Loop Engineering의 핵심은 “내가 프롬프트를 쓰는 게 아니라, 에이전트가 스스로 프롬프트를 반복하게 만드는 시스템”을 만드는 것이다.

목표를 주고, 외부 verifier(테스트, 빌드, 메트릭, 다른 에이전트)로 결과를 평가하며, 실패하면 다시 시도하고, 성공하거나 한도에 도달하면 멈춘다. Claude Code 같은 도구에서 “나는 더 이상 Claude에게 프롬프트를 쓰지 않는다. 루프를 돌린다”는 말이 나온 배경이다.

단일 루프는 잘 정의된 작업에서 강력하다. 그러나 작업이 전문화되고, 병렬화가 필요하고, 서로 다른 도구·모델·권한을 요구하거나, 검증을 생성과 분리해야 할 때 한계에 부딪힌다. 하나의 컨텍스트에 너무 많은 책임이 쌓이면 드리프트가 발생하고, 실패가 전체를 오염시킨다.

### **Graph Engineering: 조직의 Topology를 설계하다**

Graph Engineering은 다중 에이전트 시스템(또는 더 넓게는 이종 노드들의 시스템)을 **명시적인 그래프**로 다루는 실천이다.

- **노드(Node)**: 에이전트, 결정적 함수, 라우터, 조인 포인트, 도구, 인간 체크포인트. 각 노드는 자신의 루프를 돌 수 있다.
- **엣지(Edge)**: 통신, 위임, 조건부 라우팅, fan-out/fan-in, 루프백.
- **공유 상태(Shared State)**: 노드 사이를 오가는 객체(작업, 초안, 노트, 메타데이터 등). 누가 읽고 쓸 수 있는지가 명시되어야 한다.

중요한 구분은 **Org Graph**와 **Work Graph**다.

Org Graph는 비교적 안정적인 역할과 소유권(보안 에이전트는 인증·권한·감사 로그를 소유하고, 데이터 에이전트는 스키마와 마이그레이션을 소유하는 식)을 정의한다.

Work Graph는 특정 작업이 실행되면서 동적으로 형성되고 변형되는 실행 그래프다. 정책(누가 노드를 생성할 수 있는지, 상속, 실패 시 언와인딩)은 Org Graph가 통제하고, 실제 작업 흐름은 Work Graph가 반영한다.

이는 지식그래프(Knowledge Graph)와는 다르다.

지식그래프가 “시스템이 무엇을 아는가”를 구조화한다면, Graph Engineering은 “시스템이 누구인가—구성원, 권한, 메시지 경로”를 구조화한다. 둘은 공존할 수 있지만 질문이 다르다.

### **Loop 이후 AI를 어떻게 다뤄야 하는가**

Graph Engineering 시대의 핵심 원칙은 다음과 같다.

**1. 루프를 먼저 마스터하라**

그래프의 모든 노드는 결국 루프다. 약한 루프를 여러 개 연결하면 실패 지점만 늘어난다. 단일 에이전트가 안정적으로 목표를 달성하는 verifier와 stop condition을 먼저 확보해야 한다.

**2. 필요할 때만 그래프로 승격하라**

대부분의 작업은 여전히 잘 설계된 단일 루프로 충분하다. 다음 신호가 나타날 때 그래프를 고려한다.

- 작업이 명확한 전문 영역으로 나뉜다.

- 병렬 처리 후 결과를 합쳐야 한다(fan-out/fan-in).

- 단계마다 다른 모델·도구·권한이 필요하다.

- 제어 흐름을 감사 가능하고 명시적으로 만들고 싶다.

- 실패를 격리하고 싶다.

“루프에서 그래프로 졸업한다”가 아니라 “루프를 구성 요소로 사용해 그래프를 만든다”가 정확한 표현이다.

**3. Topology를 프로그래밍 가능한 아티팩트로 취급하라**

누가 존재하는지, 무엇을 소유하는지, 누구에게 말할 수 있는지, 실패 시 어떻게 되는지, 상태를 어떻게 전달하는지를 코드나 선언적으로 정의하고 버전 관리한다.

암묵적 합의나 프롬프트 속에 숨기지 않는다. 경계(maker vs checker vs authority)를 분명히 하고, 외부 현실(테스트, 메트릭, 인간 판단)을 앵커로 삼는다. 그렇지 않으면 그래프는 환각을 스케일링하는 장치가 된다.

**4. 비용, 관측성, 거버넌스를 설계에 포함하라**

그래프는 여러 루프를 동시에 돌리므로 토큰과 지연이 급증할 수 있다.

예산 캡, 라우팅(저렴한 모델로 돌리기), 시맨틱 캐싱, 승인 체크포인트를 처음부터 넣어야 한다. 실행 그래프를 기록하고, node_id / run_id 같은 식별자를 전파해 추적을 가능하게 한다. 정체성, 권한, 가드레일을 게이트웨이 수준에서 강제하는 것이 엔터프라이즈에서 특히 중요하다.

**5. 도구를 선택하되, 설계 책임을 포기하지 마라**

LangGraph(명시적 상태 그래프), AutoGen/AG2, CrewAI, Google ADK 같은 프레임워크가 노드·엣지·상태·라우팅을 지원한다.

이들은 실행 엔진이지, topology 설계를 대신해주지 않는다. “어떤 노드가 존재해야 하는가”, “어떤 실패 모드를 허용할 것인가”는 여전히 엔지니어의 몫이다.

### **간단 실전**

[langchain-ai/langgraph](https://github.com/langchain-ai/langgraph)

위 레포, 특히 examples/multi_agent 폴더에 있는 supervisor 패턴, collaboration 패턴 노트북을 먼저 돌려보라.

StateGraph로 노드·엣지·공유 상태를 명시적으로 정의하는 방식이 Graph Engineering의 핵심과 거의 1:1로 대응된다.

추가로 [langgraph-101](https://github.com/langchain-ai/langgraph-101) 레포의 multi_agent.ipynb도 좋은 입문 자료다.

빠르게 조직 구조(역할 기반)를 실험하고 싶다면 **CrewAI**가 진입장벽이 낮다. 에이전트에 role/goal/backstory를 주고 sequential 또는 hierarchical로 연결하는 방식이 “Org Graph”를 직관적으로 경험하게 해준다.

Google 생태계를 선호한다면 **ADK**(Agent Development Kit, [google/adk-python](https://github.com/google/adk-python))를 보라. 멀티에이전트 hierarchy와 graph-based workflow를 모두 지원하며, Dev UI에서 실행 그래프를 시각적으로 확인할 수 있다.

실전 적용 순서는 이렇다.

1. 먼저 잘 동작하는 **단일 루프**를 하나 만든다 (verifier와 stop condition이 명확한 것).
2. 그 루프를 “노드”로 취급하고, 전문성이 다른 두세 개의 노드로 쪼갠다.
3. 공유할 상태 스키마(TypedDict나 Pydantic)를 먼저 정의한 뒤, 노드 간 엣지(조건부 라우팅, fan-out/fan-in)를 연결한다.
4. 생성 노드와 검증 노드를 분리하고, 실패 시 재시도·에스컬레이션 경로를 명시적으로 넣는다.
5. 비용·토큰 상한을 처음부터 걸고, 실행 그래프를 로깅할 수 있게 만든다.

처음부터 복잡한 그래프를 그리려고 하지 말고, “이 작업이 단일 루프로는 더 이상 깔끔하지 않을 때”만 노드를 추가하는 습관을 들이는 것이 중요하다. LangGraph 예제 코드를 복사해서 자신의 도메인(예: 리서치 → 작성 → 리뷰)으로 바꿔보는 것이 가장 현실적인 학습 경로다.

### **마치며**

Graph Engineering은 분산 시스템과 조직 설계의 오래된 문제를 AI 에이전트에 적용한 것이다. DAG 스케줄러, 상태 머신, Actor 모델, RACI 매트릭스의 교훈이 그대로 유효하다. 새로 생긴 것은 “확률적 에이전트를 노드로 쓰는 그래프”라는 점뿐이다.

위험도 명확하다. 컨텍스트 누수, 교차 오염, 비용 폭발, 조정 실패, 검증 없는 합의(circular agreement). 이를 줄이려면 생성과 검증을 분리하고, 노드 간 권한을 최소화하며, 외부 근거에 강하게 앵커링해야 한다.

장기적으로 보면, 모델 성능이 계속 올라갈수록 “더 똑똑한 단일 에이전트”를 만드는 일의 상대적 가치는 줄어든다. 대신 **어떤 구조를 허용하고, 어떤 구조를 즉시 제거하며, 어떤 선택압을 가하는가**가 경쟁력이 된다. 잘 설계된 그래프는 그 선택압을 실행하는 환경이 된다.

### **결론**

Loop Engineering이 “한 마리의 개체를 잘 훈련시키는 일”이었다면, Graph Engineering은 “개체들이 서로를 견제하고 협력하며 실패를 격리하는 조직”을 설계하는 일이다. 루프는 죽지 않았다. 루프는 그래프의 원자 단위가 되었다.

앞으로 AI를 다루는 방식은 점점 더 “프롬프트를 잘 쓰는 것”에서 “명시적이고, 관측 가능하며, 버전 관리되는 topology를 설계하는 것”으로 이동할 것이다. 모델은 점점 더 저렴하고 강력해지지만, 그 모델을 어떤 관계망 속에 배치할지는 여전히 사람이 결정해야 한다. 그 결정의 품질이 시스템의 품질을 결정한다.

<summary><strong>[처음 배우는 AI] Prompt vs System Prompt. 요청 문장과 상위 규칙은 다르다.</strong></summary>


Prompt는 지금 시키는 말이다. "이 문장을 번역해줘", "보고서를 써줘"처럼 이번 작업의 목표, 조건, 형식, 범위를 담는다. 한 번 쓰고 끝난다.

System Prompt는 항상 지켜야 할 규칙이다. 사용자의 요청보다 위에 있고, 하면 안 되는 일을 막고, AI의 기본 역할과 답변 기준을 정한다. 대화가 아무리 길어져도 바뀌지 않는다.

선택 기준은 단순하다. 작업을 시키려면 Prompt다. 규칙을 정하려면 System Prompt다. 둘이 충돌하면 상위 규칙이 이긴다.

대부분의 사람은 Prompt만 쓴다. System Prompt를 쓰기 시작하면 AI가 "매번 말해야 하는 것"을 기억하게 된다. Prompt는 요청이고, System Prompt는 경계다. 요청은 바뀌어도 경계는 남아 있어야 한다.

여기 전체 에이전트 개발 키트가 있습니다:

Layer 1 — [CLAUDE.md](http://claude.md/) → 메모리 레이어  
아키텍처 규칙, 명명 규칙, 테스트 기대치, 리포지토리 맵. 항상 로드됩니다. 항상 활성화됩니다.  
두 가지 범위:  
• ~/.claude/CLAUDE.md → 전역  
• .claude/CLAUDE.md → 프로젝트  
이것은 매 세션 전에 붙여넣는 컨텍스트가 아닙니다. 반복할 필요가 없는 컨텍스트입니다. 에이전트의 헌법입니다.

Layer 2 — Skills → 지식 레이어  
각 SKILL.md는 설명을 담고 있습니다. Claude는 런타임에 이를 매칭하고 스킬을 격리된 서브에이전트로 포크합니다. 필요할 때만, 항상 켜져 있는 것이 아닙니다.

Layer 3 — Hooks → 가드레일 레이어  
PreToolUse → PostToolUse → SessionStart → Stop → SubagentStop

이것은 대부분의 팀이 건너뛰는 레이어입니다. 그리고 가장 먼저 후회하는 레이어이기도 합니다.

• 모든 Write에서 자동 린트

• Stop에서 Slack 알림  
이벤트 발생 → 매처 확인 → 명령 실행  
품질은 인프라 레벨에서 강제됩니다. 프롬프트 레벨이 아닙니다.

Layer 4 — Subagents → 위임 레이어  
각 서브에이전트는 자체 컨텍스트 윈도우, 모델, 도구, 권한을 가집니다.  
메인 에이전트는 아래로 위임합니다. 결과를 위로 받습니다. 그게 전부입니다.  
무한 재귀가 없습니다 — 서브에이전트는 서브에이전트를 생성할 수 없습니다. 메인 컨텍스트는 깨끗하게 유지됩니다. 설계상 강제 경계입니다.

Layer 5 — Plugins → 배포 레이어  
스킬 + 에이전트 + 훅 + 명령어를 플러그인으로 번들링하세요. 한 번 설치. 전체 팀이 동작을 상속합니다.  
npm 패키지를 생각해보세요 — 하지만 에이전트가 할 수 있는 일에 대한 것입니다.

모든 것을 감싸는:  
→ 왼쪽에 MCP 서버 (GitHub, 데이터베이스, API, 커스텀 통합)  
→ 오른쪽에 에이전트 팀 (병렬 실행, 메시지 전달, 공유 권한)

한 줄로 요약한 5-레이어 스택:  
CLAUDE.md가 규칙을 설정 → Skills가 전문성을 제공 → Hooks가 품질을 강제 → Subagents가 작업을 위임 → Plugins가 팀에 배포

<summary><strong>하네스된 LLM 에이전트, 명확히 설명!</strong></summary>


두 에이전트가 동일한 모델을 동일한 작업에 실행할 수 있고, 예상대로 완료할 수 있습니다. 하지만 그중 하나는 작업을 완료하는 데 거의 3배의 토큰을 소비할 수 있습니다.

이 추가 사용량은 그들을 감싸는 코드에서 비롯되며, 이 코드는 각 호출 시 모델의 컨텍스트에 무엇이 도달할지 결정하고 호출 횟수를 결정합니다.

예를 들어, 어떤 단계에서 50k 토큰의 JSON을 반환하는 도구를 생각해 보세요. 만약 이것이 컨텍스트에 남아 있다면, 모델은 이후 모든 단계에서 그 페이로드를 다시 읽게 될 것입니다.

도구 정의도 동일하게 작동합니다.

서버가 50개의 도구를 노출할 수 있으며, 각 도구는 이름, 설명, 입력 및 출력 스키마를 가집니다.

기본적으로, 에이전트가 사용하든 사용하지 않든 모든 도구가 첫 번째 호출부터 프롬프트에 남아 있을 것입니다.

그러나 최적화된 하네스는 모델에 불필요한 인지 부하를 피할 수 있습니다.

더 구체적으로, 하네스 엔지니어링의 핵심 설계 원칙 중 하나는 적절한 시점에 모델에서 요소들을 밀어내는 것입니다:

- 메모리는 가중치와 컨텍스트가 지니지 않아야 할 상태를 보유합니다.
- 스킬은 절차적 지식을 보유합니다. 이는 일반 모델을 전문화하는 운영 절차와 휴리스틱을 다룹니다.
- 프로토콜은 사용자, 다른 에이전트, 도구에 대한 상호작용 계약을 보유합니다.

컨텍스트가 영구적으로 사라진다는 점을 유의하세요.

필요할 때 항상 로드되며, 하네스가 얼마나 많은 양을 로드할지와 언제 로드할지를 결정합니다.

예를 들어, 50k 토큰 페이로드를 관리하기 위해 하네스는 이를 파일에 쓰고 컨텍스트에 미리보기와 경로를 유지하거나, 작업을 하위 에이전트에 넘겨 그 컨텍스트를 나중에 폐기하거나, 대화가 임계값을 초과하면 이전 메시지를 요약할 수 있습니다.

이것을 실제로 보고 싶다면, TrueForge는 이러한 관행을 이미 구현한 오픈소스 하네스입니다.

도구 스키마는 사전 로딩이 켜지지 않으면 지연되며, 대형 응답은 샌드박스 파일로 이동하고, 생성된 코드는 하네스를 통해 도구를 다시 호출하므로 샌드박스가 자격 증명을 절대 보유하지 않습니다.

위에서 언급한 두 에이전트는 DevRev의 Enterprise-Bench에서 나온 것입니다. TrueForge는 동일한 모델에서 Claude Managed Agents와 동일한 수의 작업을 해결했으며, 토큰의 3분의 1 조금 넘는 양과 약 40% 적은 도구 호출을 사용했습니다.

여기 GitHub 저장소: [http://github.com/truefoundry/trueforge](http://github.com/truefoundry/trueforge)

또한 에이전트 토큰이 실행 중에 실제로 어디로 가는지에 대한 전체 분석을 작성했으며, 컨텍스트 회계, 위 전략, 벤치마크를 자세히 다루었고, TrueForge가 이 작업을 함께 진행하는 데 도움을 주었습니다.

<summary><strong>왜 DB 설계가 중요한가. 이유는 간단하다.</strong></summary>


①한 번 데이터가 들어가면 설계 변경은 망가뜨리고 다시 만드는 것과 다름없다. 예를 들어 "users 테이블에 전화번호를 하나만 가질 수 있게 했다" → 나중에 여러 개 등록에 대응하려고 하면, 기존 데이터의 이관과 모든 참조 코드의 수정이 발생한다.

②정규화나 인덱스의 실패는 앱 쪽 코드로는 보정할 수 없다. 예를 들어 검색 대상 컬럼에 인덱스를 붙이는 걸 잊으면, 데이터가 1만 건에서는 한순간이지만 100만 건에서는 몇 초가 걸린다. 코드를 아무리 다시 써도 해결되지 않는다.

③제약 설계가 느슨하면 부정확한 데이터가 들어오고, 대증요법이 쌓인다. 예를 들어 외래 키 제약이 없어서 "존재하지 않는 사용자 ID의 주문 데이터"가 들어오면, 앱 쪽에서 null 체크의 if문이 끝없이 늘어난다.

④스케일링하는 순간에 N+1이나 JOIN 과다에 빠진다. 예를 들어 "게시물 목록 + 각 게시물의 작성자 이름"을 한 건씩 가져오는 구현은 10건이면 눈치채지 못하지만, 1000건이 되는 순간에 1000번의 쿼리가 발동한다.

코드는 다시 쓰면 된다. 하지만 DB는 고치는 데 시간도 리스크도 비교할 수 없을 만큼 든다.

<summary><strong>하네스 엔지니어링이란 무엇인가, 시각적으로 설명.</strong></summary>


![image.png](../../assets/agents/image-093.png)

에이전트 하네스는 어떻게 작동하나요?

LLM은 추론하고 텍스트를 생성할 수 있지만, 그것만으로는 신뢰성이 떨어질 수 있습니다. 신뢰성은 보통 하네스에서 나오며, 아래 다이어그램에 표시된 LLM을 둘러싼 계층입니다.

1. 사용자가 쿼리를 하네스에 보내면, 컨텍스트 빌더가 지식 베이스를 사용하여 쿼리를 프롬프트로 변환합니다.
2. LLM이 제공된 프롬프트에 대해 추론하고 일부 작업(호출할 함수)을 제안합니다.
3. 정책 게이트가 작업을 확인하고 허용할지 차단할지 결정합니다.
4. 런타임이 먼저 도구를 실행하고 결과를 LLM에 다시 보냅니다.
5. 마지막으로, 검증 단계가 결과에 대한 테스트를 실행하고 피드백을 미래 반복을 위한 컨텍스트에 포함합니다.
6. 검증 단계가 통과되면, 하네스가 결과를 사용자에게 표시합니다.

이 외에도 모든 단계에서 공유되는 두 개의 다른 계층이 존재합니다. 관찰 가능성 계층은 메트릭이나 오류 같은 것을 추적합니다. 제약 조건 계층은 시스템이 이를 시행할 수 있도록 규칙과 권한을 설정합니다.

에이전트 실패의 대부분은 컨텍스트, 도구, 제약 조건, 또는 검증 중 어디서 발생한다고 생각하시나요?

<details>
<summary><strong>만약 하네스 엔지니어링을 배우고 싶다면, 먼저 이런 걸 이해하는 걸로 시작하라고 할게:</strong></summary>


모델은 에이전트의 일부일 뿐이야.

하네스는 모델 주위의 시스템으로, 컨텍스트를 관리하고, 도구를 실행하며, 상태를 유지하고, 에이전트의 한계를 제어해.

이게 내가 제안하는 로드맵이야:

1. 에이전트 루프
    
    먼저 기본 사이클을 이해해:
    
    작업 받기 → 다음 단계 결정 → 도구 사용 → 결과 관찰 → 계속하거나 멈추기.
    
    모든 다른 건 이 루프 주위에 구축되는 거야.
    
2. 컨텍스트 엔지니어링
    
    컨텍스트에 어떤 정보가 들어갈지, 어떤 걸 빼고, 언제 회수할지 결정하는 법을 배워.
    
    지시사항, 파일, 히스토리, 도구 결과, 정보 회수, 압축을 포함해.
    
3. 도구 디자인
    
    도구는 명확한 이름, 정확한 설명, 간단한 매개변수, 검증, 유용한 응답이 필요해.
    
    결과는 컨텍스트로 돌아가서 에이전트가 다음에 할 일을 직접적으로 영향을 줘.
    
4. 상태와 메모리
    
    상태는 작업 중에 진행 상황, 계획, 중간 결과, 승인을 유지할 수 있게 해.
    
    메모리는 결정이나 선호도 같은 유용한 정보를 여러 세션 사이에 지속시켜.
    
5. 계획과 오케스트레이션
    
    계획은 작업을 단계로 나누고, 새로운 정보가 나오면 계획을 업데이트하는 거야.
    
    오케스트레이션은 모델, 도구, 하위 에이전트, 핸드오프를 조정해서 그 작업을 실행해.
    
    단일 에이전트부터 시작해. 작업이 정말로 나눌 수 있을 때 하위 에이전트를 추가해.
    
6. 권한과 가드레일
    
    에이전트가 읽고, 수정하고, 실행할 수 있는 걸 정의하고, 어떤 행동이 승인이 필요한지, 언제 멈춰야 하는지.
    
    더 많은 자율성은 더 나은 한계를 요구해.
    
7. 관찰 가능성과 평가
    
    트레이스, 도구 호출, 오류, 비용, 결과를 저장해.
    
    그 다음 실제 작업으로 평가를 구축해서 결함을 찾고, 각 변경이 시스템을 정말로 개선하는지 확인해.
    
8. 장기 실행 에이전트
    
    마지막으로, 압축, 체크포인트, 재시도, 시간과 비용 한계, 오류 복구, 작업 재개에 대해 배워.
    

왜 하네스 엔지니어링이 중요한가?

같은 모델을 가진 두 에이전트가 컨텍스트, 도구, 상태, 권한, 피드백에 따라 아주 다른 결과를 얻을 수 있기 때문이야.

# **스킬 파일**

이러한 지침은 스킬 파일 형태로 제공될 수 있는데, 이는 기본적으로 마크다운 파일로 저장된 프롬프트이며, 경우에 따라 스크립트가 함께 포함되기도 합니다. 일반적으로 스킬 파일은 모델이 특정 작업에만 필요한 워크플로에 대한 안내나 플러그인 사용 방법에 대한 지침을 제공하는 데 가장 유용합니다.

많은 사람들이 프로젝트에 여러 스킬을 한꺼번에 다운로드하는 경향이 있는데, 이는 잘못된 접근 방식입니다. 각 스킬에는 이름과 설명이 있으며, 이는 모델의 컨텍스트에 로드되어 모델이 언제 해당 스킬을 사용해야 하는지 알 수 있도록 합니다. 설명이 너무 긴 경우가 많은데, 스킬을 너무 많이 추가하면 Codex가 설명을 줄여서 컨텍스트에 맞추려고 합니다. 결과적으로 모델은 각 설명에 대한 정보를 덜 접하게 되어 어떤 스킬을 선택해야 할지 판단하기 어려워집니다.

더 심각한 것은, 설명들이 서로 모순되거나 지나치게 "나를 선택해 주세요"라는 메시지를 전달하여 모델이 실제 작업에 도움이 되지 않는 지침을 로드하게 만드는 경우입니다.

만약 여러분이 Codex에게 스킬 제작을 의뢰한 적이 있다면, Codex는 아마도 다음을 사용했을 것입니다.$스킬 크리에이터기술. 최근 실무에서 발생한 여러 실패 유형을 완화하는 데 도움이 되도록 몇 가지 방식으로 지침을 업데이트했습니다.

첫째, 스킬 설명은 모델이 언제 해당 스킬을 사용해야 하는지를 명확히 하면서 가능한 한 간결해야 합니다.

*여기서 잘못된 스킬 설명은 모델이 데이터베이스와 관련된 모든 작업을 수행할 때마다 해당 스킬을 사용하도록 만들 수 있으며, 마이그레이션을 처리해야 할 때만 사용하도록 만들지 않을 수 있습니다.*

둘째, 유용한 기술의 핵심 지표 중 하나는 점진적 정보 공개입니다. 기술을 읽는 것은 맥락을 파악하는 것으로 이어져, 기술에 더 가까워지고, 작업에 직접 적용되지 않을 수도 있는 지침까지 제공받게 됩니다. 여러 워크플로가 있는 기술의 경우, 기본 문서를 최소한의 라우터로 만들어 지원 문서와 스크립트를 가리키도록 하세요. 모델이 어디를 참조해야 하는지 알 수 있도록 충분한 지침을 제공하되, 현재 중요하지 않은 내용을 읽도록 강요하지 마세요.

셋째, 많은 기술들이 정교한 일정표나 레시피처럼 작성되었습니다. 모델들이 미묘한 차이와 모호함을 이해하는 능력이 훨씬 향상되었기 때문에, 지나치게 구체적인 지침은 예전에는 도움이 되었던 것과 달리 이제는 오히려 결과를 저해할 수 있습니다.

저장소의 기술은 다른 기여자의 에이전트에도 영향을 미치는데, 이들은 서로 다른 모델을 사용할 수 있습니다. Sol이나 Luna에게 도움이 되는 지침은 GPT-6 Astra에 과도한 제약을 가할 수 있으므로, 어떤 모델이 사용자가 남긴 지침을 사용할지 고려해야 합니다.

# **에이전트.md**

AGENTS.md 파일은 모델이 저장소에서 작동하는 모든 시점에 적용되므로, 각 지침을 다시 검토하여 해당 작업에 여전히 필요한지 확인하십시오.

오타 수정 하나 할 때마다 방대한 문서나 전체 저장소 맵을 요구하는 것은 과도합니다. GPT-6 Astra는 매 변경 전에 전체 프로젝트를 검토하지 않고도 필요한 정보만 파악할 수 있습니다.

*모델이 편집할 때마다 파일을 읽도록 하는 것은 컨텍스트를 소모하고 작업 속도를 늦추는 지름길입니다. 하지만 맥락에 맞는 문서 링크를 제공하는 것은 여전히 유용할 수 있습니다. 문서도 항상 최신 상태로 유지하세요!*

이전 모델들은 테스트를 실행하고 결과를 검증하기 위해 별도의 지시가 필요했습니다. 하지만 GPT-6 Astra는 이러한 작업을 스스로 수행하므로, 동일한 지시를 반복하면 불필요한 테스트가 발생할 수 있습니다.

# **결정 경계**

경계를 설정하는 방식에 세심한 주의를 기울이세요. 이전 모델이 허락 없이 작업을 수행했다면, 먼저 허락을 구하도록 강력한 문구를 추가했을 수 있습니다. 이는 유용할 수 있지만, GPT-6 Astra는 훨씬 뛰어난 판단력을 가지고 있으므로 그에 맞게 사용해야 합니다. 또한, GPT-6 Astra는 사용자의 경계를 진지하게 받아들이고, 사용자가 작업을 계속하기를 원하는 경우에도 작업을 중단할 수 있습니다.

# **고집**

GPT-5.6 Sol이 요청을 받고 오랫동안 작업을 계속하는 것에 익숙하다면, GPT-6 Astra는 언제 작업을 중단해야 할지 망설이는 것처럼 느껴질 수 있습니다. 첫 번째 구현을 완료한 후에도 작업이 남아 있는 상태에서 검토를 위해 다시 돌아올 수 있습니다.

이럴 때 시작하기 전에 완료 기준을 명확히 정의하는 것이 도움이 됩니다. 구현 실행, 결과 검사, 오류 수정 등이 작업에 포함된다면, 해당 내용을 요청에 명시하세요. 첫 번째 구현 후 검토를 위해 작업을 중단해야 한다는 요구사항은 모델 개발을 더 일찍 중단하게 만들 수 있으므로, 실제로 그러한 결정을 내려야 하는지 신중하게 검토해야 합니다.

첫 번째 탐색 이후에도 계속 탐색을 진행하려면 탐색할 내용과 탐색을 멈춰야 할 지점을 지정하세요.

새로운 모델을 도입하는 것은 시스템을 정비할 좋은 기회입니다. GPT-6 Astra에게 이 글에서 다룬 내용을 바탕으로 시스템 진단을 의뢰하고, 이전에는 시도조차 하지 않았던 새로운 것을 만들어 보세요!

<summary><strong>에이전트 AI 시스템 설계 개념을 간단한 언어로 이해하기:</strong></summary>

• Agent: 답변만 하는 것이 아니라 행동을 취하는 AI  
• LLM: 생각하고 결정하는 두뇌  
• Prompt: 두뇌에게 주는 지시  
• System prompt: 에이전트의 직무 설명  
• Tools: 손 (검색, 코드, API, 브라우저)  
• Function calling: 두뇌가 손을 사용하는 방법  
• Memory: 단기 메모리는 채팅이고, 장기 메모리는 영원히 기억하는 것  
• Context window: 한 번에 머릿속에 얼마나 많은 것을 담을 수 있는지  
• Planning: 큰 목표를 작은 단계로 나누기  
• Reasoning loop: 생각하고, 행동하고, 확인하고, 반복하기  
• Reflection: 에이전트가 자신의 작업을 검토하고 수정하기  
• RAG: 답변하기 전에 자료를 검색하기  
• Embeddings: 단어를 숫자로 바꿔 AI가 의미를 찾을 수 있게 하기  
• Vector database: 그 숫자들이 사는 도서관  
• MCP: AI를 어떤 앱에든 연결하는 만능 플러그  
• Orchestrator: 다른 에이전트들에게 작업을 배정하는 매니저  
• Multi-agent: 각자 하나의 직무를 가진 AI 팀  
• Sub-agents: 주 에이전트가 부수적인 작업을 위해 생성하는 도우미들  
• Guardrails: 어리석은 행동을 막는 규칙  
• Human in the loop: 위험한 부분을 당신이 승인하기  
• Evals: 에이전트가 실제로 작동하는지 확인하는 테스트  
• Observability: 무엇을 했고 왜 했는지 보여주는 로그  
• Latency: 응답하는 데 걸리는 시간  
• Token cost: 모든 생각이 당신에게 드는 비용

챗봇은 말한다.  
에이전트는 행동한다.

<summary><strong>솔직히 말해서, 요즘 많은 사람들이 AI 엔지니어링을 배우는 순서를 정말로 거꾸로 하고 있는 것 같아요.</strong></summary>

Agent, RAG, MCP, Multi-Agent, 온갖 프레임워크, 온갖 Skill, 매일 새로운 게 쏟아져 나오죠.

사람들은 웬만하면 처음부터 자율적으로 계획 세우고, 도구 호출하고, 복잡한 작업을 완수하는 슈퍼 Agent를 만들고 싶어 안달이 나 있어요.

하지만 특별히 기본적인 문제 하나, 많은 사람들이 지금까지 제대로 연구해본 적이 없을 거예요: 당신이 한段 텍스트를 대형 모델에 보낼 때, 모델이 실제로 받는 게 뭘까요?

답은 우리가 인간이 이해하는 완전한 텍스트가 아니라, Tokenizer를 거친 Token 시퀀스예요.

이렇게 별로 기술적 깊이가 없어 보이는 기본 개념 하나가, 실제로는 컨텍스트 윈도우, API 비용, 코드 생성, RAG 검색, 심지어 전체 Agent 시스템의 신뢰성까지 영향을 미치죠.

예를 들어 RAG를 할 때, 기업 지식 베이스에 있는 문서를 다양한 Chunk로 잘라야 하잖아요.

많은 사람들이 그냥 문자 길이대로 자르는데, 1000자 한 덩어리로, 이게 충분하다고 생각하죠.

하지만 문제는 문자 수와 Token 수가 전혀 다른 얘기라는 거예요.

영어, 중국어, 숫자, 코드, JSON은 서로 다른 모델의 Tokenizer에서 완전히 다른 Token 시퀀스로 쪼개질 수 있어요.

만약 Embedding 모델이 실제로 지원하는 Token 상한선을 고려하지 않으면, 문서가 잘리거나 내용이 손실되거나, 심지어 검색 효과가 떨어지는 문제가 생길 수 있어요.

더 골치 아픈 건, 어떤 문제는 직접 에러를 뱉지 않는다는 거예요.

시스템은 겉으로 정상 작동하고, API도 결과를 반환하지만, 검색할 때 정답을 못 찾는 거죠.

Embedding 모델이 형편없거나 Reranker에 문제가 있다고 생각해서半天을 헤매다, 결국 가장 앞단계인 데이터 처리에서 문제가 생겼다는 걸 깨닫게 돼요.

Agent도 마찬가지예요. 복잡한 Agent 시스템은 사용자 입력 프롬프트뿐 아니라 System Prompt, 과거 대화, 도구 호출 결과, 그리고 온갖 컨텍스트 정보를 싣고 다녀야 하죠.

이 모든 게 Token을 소비해요.

특히 Agent가 장시간 실행되면 도구 출력이 계속 쌓이고, 컨텍스트가 점점 길어지죠.

합리적인 컨텍스트 관리가 없으면 비용이 계속 올라가고, 핵심 정보가 효과적인 컨텍스트 밖으로 밀려나서 작업 성능이 떨어질 수 있어요.

그래서 요즘은 AI 엔지니어링을 배울 때 최신 프레임워크와 도구만 쫓아서는 안 된다고 느껴요.

API 호출하는 법 알겠고, 워크플로 설정하고, 몇 가지 Skill 설치하는 거, 물론 유용하죠.

하지만 시스템에 진짜 문제가 생겼을 때, 당신이 문제를 해결할 수 있는지를 결정짓는 건 보통 평소에 별것 아니라고 여겼던 기본 지식들이에요.

예를 들어 Tokenization, Context Window, Embedding, Retrieval, 비동기 작업, 상태 관리, 재시도 메커니즘, 멱등성, 그리고 모델 출력의 신뢰성을 어떻게 평가할지 같은 거요.

이런 것들은 따로 떼어놓고 보면 새 Agent 프레임워크만큼 매력적이지 않을 수 있어요.

하지만 AI 시스템을 기업에 제대로 인도해서 실제 비즈니스를 지속적으로 처리하게 하려면, 이런 기본들은 절대 피할 수 없어요.

제가 AI를 처음 접한 후부터 지금 기업 GEO, Agent, 자동화 워크플로를 다루면서 가장 깊이 느낀 건: 데모로 보여줄 수 있는 AI를 만드는 것과, 안정적으로 장기 운영할 수 있는 AI 시스템을 만드는 건 완전히 다른 난이도라는 거예요.

데모는 가장 이상적인 상황만 보여주면 돼요.

하지만 실제 비즈니스에서는 사용자가 형식 엉망인 파일을 업로드하거나, 예상치 못한 질문을 던지거나, API가 타임아웃 걸리거나, 도구 호출이 실패하거나, 지식 베이스가 올바른 내용을 검색 못 할 수 있어요.

이런 문제들은 더 강력한 모델로 바꾼다고 무조건 해결되는 게 아니에요.

데이터가 모델에 어떻게 들어가는지, 모델이 어떤 정보를 볼 수 있는지, 시스템이 어떤 상황에서 실패하는지, 그리고 실패 후 어떻게 처리할지를 알아야 해요.

그래서 원문에서 언급한 한 가지 변화에 특히 공감해요: 과거 데이터 과학을 배울 때는 모델 자체를 이해하는 데 초점이 맞춰졌어요.

하지만 AI 엔지니어링 단계에 이르면, 모델 주위에 구축된 전체 시스템을 이해해야 해요.

사용자 입력부터 Tokenization, 검색, 컨텍스트 조립, 모델 추론, 도구 호출, 그리고 최종 결과 검증까지, 모든 층이 시스템의 신뢰적 작동을 결정짓죠.

물론 Tokenization을 이해한다고 갑자기 훌륭한 AI 엔지니어가 되는 건 아니에요.

하지만 이런 기본조차 이해하지 않고 점점 복잡한 Agent를 서둘러 구축하면, 나중에 이런 어색한 상황에 빠지기 쉽죠:

시스템이 돌아갈 때는 자신 뭐든 다 안다고 느끼지만.

시스템이 안 돌아갈 때는 어디서부터排查을 시작할지조차 모르는 거예요.

AI 도구들은 개발의 문턱을 낮추고 있지만, 시스템을 이해할 필요성을 없애진 않아요.

오히려 코드와 워크플로가 점점 쉽게 생성되기 때문에,底层 메커니즘을 이해하고 기술 선택을 판단하며 복잡한 문제를 위치 지을 수 있는 사람들이 더 중요해질 거예요.

저는 미래 AI 엔지니어들 사이의 격차가, 누가 더 많은 프레임워크를 아는지나 GitHub 저장소를 더 많이 모았는지로 생기는 게 아닐 거라고 봐요.

시스템에 문제가 생겼을 때, 왜 실패했는지 제대로 파악하고 엔지니어링 방법으로 문제를 해결할 수 있는 사람이에요.

항상 최신 도구만 쫓지 마세요. 가끔 뒤돌아보면서 Token, 컨텍스트, 검색, 시스템 신뢰성 같은 기본을 다시 한 번 공부하는 게, 열 개 Agent 프레임워크를 더 파는 것보다 유용할 수 있어요.

결국 모델 호출은 쉽지만, AI 시스템을 진짜 이해하고 다루는 게 진짜 엔지니어링 능력이니까요.

</details>

<details>
<summary><strong>AI 에이전트 엔지니어링은 곧 기술 분야에서 가장 수요가 높은 기술이 될 것입니다.</strong></summary>

모두가 AI 에이전트를 만들고 있습니다. 거의 아무도 신뢰할 수 있는 워크플로를 설계하지 않습니다.

이 6가지 에이전트 패턴을 마스터하면 AI 엔지니어 상위 1%에 들게 될 것입니다

1. 라우팅
    
    에이전트의 요청 라우팅 워크플로우.
    입력값을 분류하고 적절한 모델, 프롬프트, 도구 또는 워크플로우로 전송합니다. 서로 다른 요청은 서로 다른 경로를 사용합니다.
    라우팅 실패 또는 모델 호출은 재시도 및/또는 대체 처리 처리가 필요할 수 있습니다.
    
2. 병렬화
    
    에이전트의 병렬 실행 워크플로우.
    많은 사전 정의된 작업을 동시에 실행한 후, 그 결과를 결합합니다. 섹셔닝은 서로 다른 작업을 병렬로 실행하는 반면, 투표는 동일한 작업을 여러 번 실행합니다.
    병렬 작업은 독립적으로 실패할 수 있으므로, 선택적 재시도와 부분 실패 처리가 필요합니다.
    
3. Orchestrator-Workers
    
    에이전트의 작업 위임 워크플로우.
    중앙 LLM이 작업을 하위 작업으로 분해하고, 이를 워커들에게 할당하며 그들의 결과를 결합합니다. 오케스트레이터는 실행 중에 동적으로 어떤 하위 작업이 필요한지 결정합니다.
    워커 실패는 작업을 부분적으로 완료된 상태로 남길 수 있으므로, 복구 메커니즘이 필요합니다.
    
4. 도구 사용
    
    에이전트의 도구 실행 워크플로우.
    LLM이 API, 데이터베이스, 검색 등의 외부 도구를 선택하고 호출하여 작업을 완료합니다. 도구 결과는 에이전트가 다음에 무엇을 할지 결정하는 데 사용할 수 있는 정보를 제공합니다.
    도구 호출은 실패하거나/타임아웃될 수 있으므로, 제한된 재시도와 멱등성을 필요로 합니다.
    
5. 반성
    
    에이전트의 자기 검토 워크플로.
    LLM이 자신의 출력을 검토하고, 문제점을 식별하며 결과를 수정하여 품질을 향상시킵니다. 에이전트는 품질 임계값을 충족하거나 중지 한계에 도달할 때까지 이 과정을 반복합니다.
    반성은 루프에 갇힐 수 있습니다. 따라서 반복 한계와 복구를 위한 저장된 진행 상황이 필요합니다.
    
6. 계획 수립
    
    에이전트의 작업 계획 워크플로우.
    LLM이 복잡한 목표를 단계로 분해하고, 이를 실행하며 필요할 때 계획을 수정합니다. 에이전트는 단계 간 의존성을 관리하고 실행이 실패할 때 계획을 조정합니다.
    후속 단계가 실패할 수 있으므로, 실행을 재개하기 위한 체크포인트와 복구 메커니즘이 필요합니다.

<details>
<summary><strong>LLM을 학습에 적용할 때 염두해두면 좋은 학습이론</strong></summary>

1. 바람직한 어려움(desirable difficulty)  
고생해가며 인지적 노력을 많이 들여 공부한 것이 파지(retention)을 좋게함. 답이 뭔지, 해설을 해달라고 해서 끄덕끄덕하면 당장은 아는 것 같지만(유창성; fluency) 실제 역량으로 이어지기 어려움  
2. 의도적 연습(deliberate practice)  
엄청 어려운 문제를 몰입해서 긴장된 상태로 즉각적인 피드백을 받아가면서 연습하는 것이 전문가 수준의 능력을 배울 수 있게 함. 의학교육에서 많이 언급되고 도제식 교육이 이것 바탕임. AI 딸깍으로 답을 얻는 걸로는 이루어지지 않음.  
3. 인지부하 이론(cognitive load theory)  
제한된 작업기억을 이용해 학습할 때 효율적으로 해야함. 내재적 부하는 관리, 외재적 부하는 최소화, 본유적 인지부하는 학습자가 최대한 거치도록 해서 스키마 형성을 촉진해야 함. 스키마 = 구조화된 장기기억속 지식. 새로 배우는 걸 기존에 통합해야함  
4. 전문성 역전 효과(expertise reversal effect)  
초심자에게 LLM이 청산유수로 설명해주면 스키마 구성 기회를 박탈할 수 있음  
스키마가 이미 확립된 전문가에서는 빈곳을 채워 강화시켜주는 효율적 활용이 가능, 단 너무 의존하면 숙련저하(deskilling) 위험  
발달 단계별 AI 적용 방식이 달라져야함

번외. productive failure / error-based learning  
내가 예상한 답이 있고, AI가 주는 답과 비교하는 접근이 학습자 입장에서 가장 중요하다고 봄. 예상과 다른 부분이 내가 공부할 포인트가 되는 거고, 때로는 AI의 실수를 잡아내는 단서가 됨. 예상하지 못하면 검증하는 것이 불가능함.

나도 논문 볼 때 LLM 요약 읽기 -> 탐독 -> 내가 이해한 걸 한 문단 정도 적어봄 -> LLM에게 틀리거나 빠뜨린 내용 피드백 받기 이런 과정을 거쳐서 공부하고 있다. 내가 체득한 LLM 활용한 가장 효율적인 공부방법이라고 생각함

</details>

<summary><strong>하니스 엔지니어링 2.0이 출시되었습니다!</strong></summary>

S도구 프로토콜, 에이전트 통신, 에이전트 인터페이스에 이어 이제 하니스에도 프로토콜이 생겼습니다.

개발자들이 UHP(Unified Harness Protocol)를 개발했습니다. 이는 모든 에이전트 하니스에서 에이전트 작업을 실행하기 위한 표준화된 인터페이스입니다.

HarnessRouter는 오픈소스 서버 구현체입니다.

작동 방식은 다음과 같습니다:

- 제품 백엔드에서 `harness_id`와 함께 작업을 보냅니다.  
- HarnessRouter가 선택된 하니스를 자체 세션에서 시작합니다.  
- 하니스가 네이티브 에이전트 루프를 실행하고 진행 상황을 스트리밍합니다.  
- 파일, 아티팩트, 실패, 최종 출력이 동일한 인터페이스를 통해 반환됩니다.

UHP 없이 모든 하니스를 통합하려면 작업 실행, 세션, 스트리밍, 파일, 복구, 출력 형식에 대한 별도의 처리가 필요합니다.

UHP를 사용하면 Codex, Claude Code, Gemini CLI, Hermes, Pi 및 기타 하니스들이 네이티브 도구, 기술, 모델, 에이전트 루프를 유지하면서 동일한 제품 백엔드에 연결할 수 있습니다.

이로 인해 개발자들은 다음을 할 수 있습니다:

- 제품 통합을 다시 구축하지 않고 하니스를 전환할 수 있습니다.  
- 동일한 작업을 서로 다른 하니스에서 실행할 수 있습니다.  
- 또 다른 실행 스택을 유지하지 않고 새로운 하니스를 추가할 수 있습니다.

HarnessRouter는 현재 30개의 하니스 베이스를 지원합니다.

리포지토리는 여기 있습니다: http://github.com/HarnessRouter/harnessrouter

(별표를 잊지 마세요 ⭐)

공식 벤치마크에 따르면, 모델을 고정하고 하니스만 변경했을 때 여러 헬스케어 규정 준수 작업에서 비용이 25%에서 64%까지 감소했습니다.

하니스와 모델을 모두 변경하면 최고 비용 구성과 최저 비용 구성 간 차이가 99.8%로 확대되었습니다.

개발자들은 Harness Arena를 사용하여 서로 다른 구성에서 자체 워크로드를 테스트할 수 있습니다.

Alibaba Cloud의 Qoder도 UHP를 채택하여 HarnessRouter API를 통해 에이전트 백엔드로 사용할 수 있게 되었습니다.

더 깊이 파고들고 싶다면, 모델 라우팅이 하니스 라우팅과 어떻게 다른지, 여러 에이전트 런타임을 지원하는 것이 실제로 무엇을 포함하는지 설명하는 기사를 이미 작성했습니다.

이 기사는 UHP, 로컬 설정, 작동하는 API 호출, 세션과 파일 작동 방식을 다룹니다.

<summary><strong>MCP는 어떻게 작동하나요?</strong></summary>

Claude에게 이렇게 요청하세요: “Notion에서 회의 노트를 찾아서 미결 사항을 요약해 줘”.  

이걸 하려면 Notion에 접근해야 해요. 그 연결이 없으면, 노트를 직접 검색해서 채팅에 복사해야 할 거예요.  

MCP (모델 컨텍스트 프로토콜)는 에이전트(Claude)를 다른 시스템과 연결하는 표준 방식을 정의해서 데이터를 조회하고 작업을 수행할 수 있게 해요.  

Notion은 MCP 서버를 제공해요. 이건 요청을 받아서 당신의 계정에서 권한에 따라 실행하는 프로그램이에요.  

연결되면 과정은 이래요:  

1) Claude가 Notion에서 할 수 있는 걸 물어봐요. 서버가 사용 가능한 작업(페이지 검색이나 읽기 등)을 설명하고, 각 작업에 필요한 데이터를 알려줘요.  

2) 그다음 회의 노트를 검색해 달라고 요청해요. 서버가 Notion에서 검색해서 찾은 페이지를 반환해요.  

3) 관련 페이지 읽기를 요청하고 내용을 받아요.  

4) 그 정보를 바탕으로 미결 사항 요약을 준비해요.  

모델이 당신의 요청을 해석해서 필요한 걸 결정하고, MCP 서버가 실제 데이터에 대한 작업을 실행할 수 있게 해요.  

왜 표준이 중요한가요?  

웹과 앱이 같은 API를 사용할 수 있는 것처럼, Claude와 Cursor가 Notion의 같은 MCP 서버를 쓸 수 있어요.  

하나(Claude)는 회의를 요약하고, 다른 하나(Cursor)는 문서를 저장할 수 있어요. 용도는 달라지지만, 각각에 별도의 통합을 만들 필요가 없어요.
