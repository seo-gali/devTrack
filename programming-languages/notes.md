<details>
<summary><strong>어떤 Java 컬렉션을 사용해야 할까요?</strong></summary>

• 리스트가 필요하다면? 거의 항상 ArrayList.  
• 큐나 스택이 필요하다면? ArrayDeque. Stack이나 LinkedList는 사용하지 마세요.  
• 고유한 항목이 필요하다면? HashSet.  
• 고유하고 삽입 순서대로 유지해야 한다면? LinkedHashSet.  
• 고유하고 정렬되어야 한다면? TreeSet.  
• 항상 가장 작은 또는 가장 큰 항목이 필요하다면? PriorityQueue.  
• 열거형 키가 필요하다면? EnumMap.  
• 읽기 작업이 많고 쓰기 작업이 매우 적으며, 여러 스레드가 사용된다면? CopyOnWriteArrayList.  
• 여러 스레드에서 공유되는 맵이 필요하다면? ConcurrentHashMap.

</details>

<details>
<summary><strong>Java는 사태에 늦게 도착하는 언어입니다. 제가 증명해 보이죠</strong></summary>

람다, 레코드, 가상 스레드, 제네릭. 많은 다른 언어들이 훨씬 전에 이미 가지고 있었죠.

이제 여러분은 이렇게 생각할 수 있겠네요:

- 엘더, 자바를 까는 거예요?
- 전혀요. 제게 이는 자바의 큰 장점 중 하나예요.

왜 그런지 말씀드리기 전에, 늦게 도착하는 데 전문가인 회사를 떠올려 보세요: 애플. 애플은 태블릿을 최초로 출시한 회사가 아니었고, 아이폰 같은 스마트폰이나 아이팟도 아니었어요. 항상 늦게 도착했죠. 그리고 늦게 도착하는 장점은 뭘까요? 다른 사람들이 저지른 실수를 피할 수 있다는 거예요.

제 절친한 친구 한 명이 말하길, 자바는 항상 프로덕션 언어였다고 해요.

- 그래요, 하지만 모든 언어가 프로덕션 언어잖아요.
- 맞아요, 모든 언어는 프로덕션에 배포하기 위해 만들어지죠. 하지만 모든 생태계가 무언가를 출시하기 전에 프로덕션을 먼저 바라보는 문화를 가진 건 아니에요. 자바에서는 그게 항상 최우선 과제였어요.

실제적인 결과는? 람다, 레코드, 가상 스레드, 제네릭, 그리고 수많은 다른 기능들이 프로덕션에서 버그 없이 들어갔다는 거예요. "와, 레코드가 구현을 잘못해서 프로덕션에서 터졌어" 같은 이야기는 찾기 어려울 거예요.

저는 27년 동안 이 분야에 있었고, 자바가 다른 생태계보다 먼저 무언가를 출시하기 위해 서두르는 일은 절대 없을 거라고 생각해요. 그리고 제게 이는 커리어 교훈이기도 해요. 정말로 무언가를 최초로 하기 위해 서둘러야 할까요? 잘 모르겠어요. 시장에서 30년 이상 된 언어를 보면서도 여전히 다른 어떤 언어보다 진화하고 있는 걸 보니, 그들은 자신이 하는 일을 잘 알고 있다는 생각이 들어요.

</details>

<details>
<summary><strong>2026년 자바의 90%는 이 10가지 개념을 마스터하는 데 달려 있습니다:</strong></summary>

1. 메모리 모델 + happens-before  
volatile이 실제로 보장하는 것, Double-Checked Locking이 여전히 문제를 일으킬 수 있는 이유, 그리고 안전한 게시(safe publication)가 어떻게 작동하는지 알아야 합니다.  
2. 동시성 기본 요소  
올바른 도구 선택: synchronized vs ReentrantLock vs atomics vs 동시성 컬렉션; 스레드 누출과 무제한 실행자(executors)를 피하세요.  
3. GC와 할당 동작  
GC 로그를 읽고, 일시 중지(pause)와 처리량(throughput) 간의 트레이드오프를 이해하며, 핫 루프에서 우발적인 할당 폭풍을 멈추세요.  
4. 프로파일링, 추측이 아닌  
async-profiler/JFR을 사용해 CPU, 잠금 경합, 할당 핫스팟을 찾으세요; 플레임 그래프는 직관을 항상 이깁니다.  
5. 현대적 IO와 백프레셔  
NIO, 요청당 스레드 제한, 그리고 느린 다운스트림이 큐 성장, 타임아웃, 재시도 폭풍을 일으키는 방식을 이해하세요.  
6. API와 데이터 경계  
null 가능성, 불변성, 스키마 진화에 엄격하세요; 대부분의 프로덕션 버그는 계약(contract)이 표류(drift)하면서 발생합니다.  
7. 의존성 관리  
Maven/Gradle 충돌, shaded jar, CVE, 재현 가능한 빌드; CI와 프로덕션에서 동일한 코드가 다르게 동작하는 이유를 알아야 합니다.  
8. 확장 가능한 관찰 가능성  
추적/스팬 ID가 포함된 구조화된 로그, 유용한 메트릭(p95/p99, 포화도), 그리고 하나의 나쁜 고객을 지우지 않는 샘플링.  
9. 선택적이지 않은 보안 기본  
역직렬화 가제트, SSRF, 비밀 처리; TLS를 올바르게 사용하고 내부 엔드포인트에서도 입력을 검증하세요.  
10. 실패 모드와 재시도  
멱등성 키, 모든 곳의 타임아웃, 지터가 포함된 제한된 재시도; 시스템을 녹이는 가장 빠른 방법은 500 오류에 대한 무한 재시도입니다.  

</details>

<details>
<summary><strong>프로그래밍 언어에 푹 빠진 프로그래밍 언어 괴짜로서, 2년 넘게 프로그래밍 언어를 개발해 온 나로서는 "프로그래밍 언어를 작성한다"는 게 왜 그렇게 쉽지 않은지 내 나름의 말로 설명해 보겠다.</strong></summary>

해결해야 할 첫 번째 문제는 코드 에디터에서 보는 그 멋진 하이라이트된 텍스트를 CPU가 실제로 실행할 수 있는 무언가로 바꾸는 것이다.  

여기서 프로그래밍 언어는 크게 3가지 범주로 나뉜다:  

1. 컴파일 언어.  
2. 인터프리터 언어.  
3. 둘의 혼합.  

컴파일 언어로 시작해 보자. 컴퓨터 작동 원리를 잘 모르는 사람에게는 이게 이 문제를 해결하는 가장 명백한 방법처럼 보일 수 있다.  

CPU는 "기계 코드"라는 걸 실행하는데, 이는 기본적으로 아주 간단한 명령어들의 시퀀스다. 예를 들어:  

1. 두 숫자 더하기  
2. 결과를 메모리에 저장하기  
3. 그로부터 새로운 숫자 빼기  
4. 그 숫자를 10과 비교하기  
5. 다르다면 1단계로 돌아가기   
6. 메모리에서 새로운 숫자 읽기  
7. 메모리에서 두 번째 숫자 읽기  
8. 그 두 숫자 곱하기  
...  

컴퓨터 작동 원리를 깊이 이해하지 못하면 믿기 힘들겠지만, 이게 바로 당신이 상상할 수 있는 모든 것—트위터, GTA VI, 팔콘 9, 인스타그램 릴스에서 무한 스크롤하는 알고리즘, 그리고 ChatGPT 뒤의 신경망—의 뒤에 숨은 명령어들이다.  

이 명령어들은 이진 형식으로 인코딩되며, CPU는 1과 0만 다룰 수 있다.  

예를 들어, AMD와 인텔이 사용하는 x86 기계 코드에서 "두 숫자 더하기"는 이런 식일 거다:  

01001000 00000001 11011000  

스마트폰과 애플의 새로운 맥북에서 사용하는 ARM 어셈블리에서는:  

10001011 00000010 00000000 00100000  

이진 코드를 작성하는 건 너무 지루하고 오류가 발생하기 쉽다(잘못된 단 하나의 0이나 1이 전체 프로그램을 망친다). 그래서 엔지니어들은 이를 더 쉽게 하기 위해 "어셈블리"를 발명했는데, 이는 영어와 더 비슷하다. ARM에서 숫자 더하기와 빼기 명령어는:  

𝚊𝚍𝚍 𝚛𝟷, 𝚛𝟸, 𝚛𝟹  
𝚜𝚝𝚛 𝚛𝟹, [𝚡𝟹]  
𝚜𝚞𝚋 𝚛𝟹, 𝚛𝟺, 𝚛𝟹  
𝚌𝚖𝚙 𝚛𝟺, 𝟷0  

이것들은 더하기, 저장하기, 빼기, 비교하기를 위한 "기억조어"다. "r1, r2, r3"은 레지스터로, CPU가 숫자를 저장할 수 있는 곳이며 수량이 제한적이다—예를 들어 AMD/인텔 CPU에는 16개가 있다. 그리고 저장 명령어의 x3은 메모리 위치로, 메모리에는 기가바이트 단위의 데이터를 저장할 수 있지만 CPU에서는 가진 레지스터 수만큼만 작업할 수 있다.  
이게 중요한 이유는 메모리에 읽고 쓰는 게 느리기 때문이다.  

그래도 인간으로서 나는 "이 숫자를 10과 비교하라" 같은 걸 쓰고 싶지 않다. 장바구니에 아이템이 10개 이상이면 "할인 적용하기" 같은 걸 쉽게 표현하고 싶다.  

그게 바로 프로그래밍 언어가 해주는 일이다. 당신은 이런 식으로 쓸 수 있다:  

𝚒𝚏 𝚞𝚜𝚎𝚛.𝚌𝚊𝚛𝚝.𝚒𝚝𝚎𝚖𝚜.𝚌𝚘𝚞𝚗𝚝() > 𝟷0 {  
    𝚞𝚜𝚎𝚛.𝚌𝚊𝚛𝚝.𝚊𝚙𝚙𝚕𝚢_𝚍𝚒𝚜𝚌𝚘𝚞𝚗𝚝()
}  

이건 어떤 인간에게나 기계 코드나 어셈블리 코드보다 훨씬 읽기 쉽고 이해하기 쉬운, 몇 배나 더 나은 방식이다.  

그래도 바로 저기 있는 그 멋진 if 문은 CPU에서 실행되기 위해 기계 코드로 변환되어야 한다. 게다가 한 가지 기계 코드로만이 아니라, 코드가 윈도우 PC, 맥, 서버 등 어디서나 실행되길 바란다면 각 타겟에 맞는 여러 유형의 기계 코드로 변환되어야 한다.  

이제 질문은 "어떻게"가 된다. 영어처럼 보이는 무언가를 어떻게 1과 0으로 바꾸나?  

첫 번째 단계는 "파싱"이다. 당신이 상상하는 "100가지 규칙"을 가진 형식 문법인 그 텍스트를 읽고, 나중에 기계 코드로 바꿀 수 있는 무언가로 바꾸는 프로그램을 작성해야 한다.  

보통 여러 단계를 거치는데, 이는 벽돌을 만들려면 먼저 원료를 추출한 후 그것을 가공해서 나중에 벽돌로 변환할 수 있는 새로운 재료를 만드는 공장처럼 상상해 보라.  

또는 마인크래프트의 크래프팅처럼 상상해 보라.  

파서가 추출하는 "재료"는 "추상 구문 트리"다. 이는 본질적으로 메모리에 저장된 데이터 구조(텍스트 대신 메모리에 조직된 데이터)로, 프로그램을 더 쉽게 처리할 수 있게 만든다.   

</details>

<summary><strong>요즘 Rust 좋다, Rust가 뜬다 하는데 정작 왜 좋은지 설명하는 글은 별로 없음.</strong></summary>

핵심은 메모리를 관리하는 방식에 있음  

JavaScript는 GC가 실행 중에 필요 없는 메모리를 정리하고,  
C/C++은 개발자가 메모리를 직접 관리하는 경우가 많음  

그런데 Rust는 접근 방식이 다름  

“메모리를 잘못 사용할 코드는 애초에 컴파일하지 말자.”  

이걸 가능하게 하는 게 Ownership(소유권)과 Borrow Checker임  

모든 값에는 소유자가 있음  
소유자가 사라지면 메모리가 정리됨  
다른 곳에서 데이터를 빌려 쓸 수 있지만, 안전한 규칙을 지켜야 함  
컴파일러가 이 규칙을 검사함  

그래서 뭐가 좋냐면,  

GC 없이도 메모리를 관리할 수 있음  
Use-after-free, Double-free 같은 메모리 오류를 방지함  
네이티브 코드로 컴파일돼 높은 성능을 낼 수 있음  
잘못된 메모리 접근을 실행 전에 상당 부분 잡아냄  

즉, C/C++ 수준의 성능을 추구하면서 메모리 안전성까지 확보하려는 언어라는 것  

물론 Rust도 만능은 아님  
학습 난도가 높고, 메모리 누수나 논리적 보안 취약점까지 전부 막지는 못함  

그런데 AI 코딩 시대에는 이 특징이 더 흥미로워짐  

AI가 Rust 코드를 작성 → 컴파일러가 소유권,타입 오류를 발견 → AI가 수정  

사람이 어려워하던 부분을 AI가 보완하고, 컴파일러는 엄격하게 검사하는 구조  

Rust가 주목받는 이유는 단순히 빠르기 때문이 아니라,  

안전성을 실행 중 관리하는 대신 가능한 많은 문제를 컴파일 단계에서 해결하도록 설계했기 때문임  

언어는 만들어진 이유와 원리를 같이 파보면 재밌다ㅋㅋㅋㅋ
